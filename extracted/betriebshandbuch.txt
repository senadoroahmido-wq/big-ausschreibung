Diese Dokumentation beschreibt alle relevanten Informationen über den Aufbau und den Betrieb des Gesamtsystems.
Bei dem Betriebshandbuch handelt es sich um ein lebendes Dokument, in das sämtliche Änderungen eingetragen werden.
Basis für den Aufbau ist die Struktur des gültigen Vertragswerkes zwischen der PROACT und dem Kunden.

MPLS Standortmigration
Das Proact MPLS wird parallel zum bestehenden MPLS aufgebaut und hat keinen Einfluss auf die Infrastruktur der actimonda und BIG Standorte.
Folgende Migrationsschritte und Hinweise sind hier festgehalten:
Der Standort X erhält einen neuen Router für den Standort von der Webdiscount.
Die Default-Gateway-Adressen der Standort-Netzwerke werden übernommen (siehe IP-Subnetzliste).
Zum Umschaltungszeitpunkt wird das Netzwerkabel vom bestehenden MPLS-Router auf den neuen Router gesteckt. Die verschiedenen Subnetzwerke werden via VLAN-Tagging an den Router übergeben.
Zwecks OSPF-Routing ist der Weg zur Proact Cloud Frankfurt gesichert und durch die Direktverbindung zur itsc der Zugriff auf die Ressourcen gewährleistet, sofern die Netzwerkumschaltung vor der Dienste-Transition durchgeführt wird.
Anpassung des Routings für den Standort Seitens der itsc in Richtung DIrekverbindung Proact, damit der Standort über den neuen Weg das itsc erreicht.
Zwecks Fail-Back kann das Netzwerkkabel auf den „alten“ MPLS-Router zurückgesteckt werden, sofern die Verbindungen nicht funktionieren.

CodeTwo Exchange Rules Pro
Allgemeines
Auf dem Mailserver vmail02 ist die Software CodeTwo Exchange Rules Pro (Exchange Rules Pro  Admin Panel und Exchange Rules Pro Service) installiert.
Das Tool ist eine Erweiterung für den MS Exchange-Servers und klinkt sich in den Mail-Flow des Exchange Servers ein.
Über definierte Regeln wird der Mail-Flow und der Inhalt von E-Mails (in- und outgoing) gesteuert. Mail-Signatur, Bounce, Weiterleitung von a an b etc erfolgt zum größten Teil über CodeTwo.
Andere Regeln sind im Exchange konfiguriert.
Konfiguration
Der Zugriff auf die Software erfolgt mittels Rechten, die in der Anwendung gesetzt werden und den angemeldeten Windows Benutzer, der abgefragt wird.
Jeder Exchange Server (im Cluster) muss mind. den Service "Exchange Rules Pro Service" installiert haben, damit korrekt die Regeln beim Mail-Flow angewendet werden können.
Installation
- Der MSExchangeTransport Dienst wird während der Installation der Software gestoppt.
- Es wird  das MS .NET FW benötigt.
Es wird für jede Installation eine eigenständige/separate S/N - Lizenzschlüssel für die Software benötigt, die beim Hersteller Support bestellt werden muss.
Der Installationsprozess ist unter dem Link: https://www.codetwo.com/userguide/exchange-rules-pro/software-installation.htm zu finden.
Lizenzen
Die Lizenzen werden von der BIG beigestellt.
Zertifikate

Das externe Wildcard wird ebenfalls für die Hybridstellung verwendet.

Des Weiteren besteht die Anforderung die Postfächer weiterhin OnPremises auf der Exchange Infrastruktur zu hosten.

Citrix License Activation Service (LAS)
Der Citrix License Activation Service (LAS) ist das neue, cloudbasierte Lizenzierungsmodell von Citrix, das die bisherige dateibasierte Lizenzierung vollständig ersetzt. Statt Lizenzdateien manuell herunterzuladen, hochzuladen und zu verwalten, kommuniziert der Lizenzserver direkt mit Citrix Cloud und bezieht Berechtigungen automatisch.
LAS arbeitet nach einem kontinuierlichen Online-Aktivierungsmodell:
Der Lizenzserver wird einmalig bei Citrix Cloud registriert.
Berechtigungen werden automatisch alle 12-24 Stunden von LAS synchronisiert.
Jedes Produkt erhält eine rollierende 30-Tage-Aktivierungsperiode, die bei bestehender Verbindung automatisch erneuert wird.
Bei Verbindungsunterbrechung greift ein License-Cache-Modus (30 Tage Puffer).

Zusätzlich zu den bereits eingesetzten FSLogix Profile Containern wurde für die Citrix-Benutzerumgebung eine FSLogix Office 365 Container (ODFC)-Konfiguration eingeführt.Ziel dieser Erweiterung ist die Bereitstellung von Outlook Cached Mode innerhalb der Citrix-Sitzungen auf Basis der Microsoft Best Practice. Neben Outlook werden dabei auch weitere Office-bezogene Daten, insbesondere OneNote, im ODFC-Container berücksichtigt.

Citrix/Azure Mulitfaktor Authentifizierung Einführung
Multi-Faktor-Authentifizierung ist ein Prozess, bei dem Benutzer während des Anmeldevorgangs zur Durchführung eines weiteren Identifizierungsverfahrens aufgefordert werden, z. B. per Eingabe eines Codes auf dem Smartphone oder per Fingerabdruckscan.
Die BIG verwendet Azure-MFA als Multifaktor Lösung für den Zugriff auf Citrix Ressourcen via URL: https://citrixmfa.big.krankenkasse.de.
Beim Aufruf dieses URLs wird der Client an die Authentifizierung Webseite von Microsoft weitergeleitet wo nun die spezifischen Authentifizierung Anforderungen angewendet werden die per Azure Active Directory Konfiguriert worden sind. In diesem Fall werden ist die folgenden Authentifizierung Methoden angewendet:
One-Timepassword + FIDO2 Auth.
Azure MFA Mobile-App (geringer User Kreis)
Die Option „MFA pro Benutzer“ muss für die Konfiguration mit einem FIDO key deaktiviert sein.
Bei Benutzern die den FIDO Key wie auch ein Mobile-App mit OTP verwenden möchten müssen diese Option „Erzwungen“ haben.
Zusätzlich sind Global-Administratoren auch mit diese einstellung versehen um zusätzliche sicherheit zu gewehrleisten.

big-vqwrk01
Der big-vqwrk01 ist eine Quarantäne VM. Mit dem CR#4659 wurde ein Skript erstellt, welches die VM immer wieder zurück auf einen sauberen Stand setzt. Das Skript wird auf dem Jenkins Server der Proact vCloud täglich um 04:00 Uhr ausgeführt.
Das Skript wurde so erstellt, dass immer auf den zuletzt erstellen Snapshot zurückgesetzt wird. Damit ist sichergestellt, dass nach Updates ebenfalls nichts verloren geht.
Die Logik des Skripts ist folgende:
Prüfen welche Snapshots vorhanden sind
Wenn ein Snapshot älter als 6 Tage alt ist
Restore des letzten Snapshots und Start der VM nach Restore
Löschen des ältesten Snapshots
Erstellen eines neuen Snapshots
Ansonsten Restore des letzten vorhandenen Snapshots und Start der VM nach Restore
Mit dem Zyklus von 6 Tagen wird Monitoringmeldungen vorgebeugt, welche ein unerwünschtes, manuelles Löschen von Snapshots zur Folge haben könnte.

Managed Services
Das Proact Service Operation Center (SOC)
Beschreibung und Ziele
Das Proact Service Operation Center (SOC) ist nach den Richtlinien und Best-Practice-Ansätzen von ITIL V3 strukturiert und aufgebaut und kann skalierbar für den IT-Betrieb der Proact Kunden eingesetzt werden. SOC-Dienstleistungen werden, je nach Bedarf, in einem Spektrum von reaktivem Support bis hin zu einer kompletten Betriebsverantwortung definiert und umgesetzt. Dabei spielt es keine Rolle, ob der Kunde seine IT-Infrastruktur bei sich vor Ort (On-Premises) oder in einem der zwei Proact-Rechenzentren in Frankfurt betreibt (Proact Cloud).
Der Grad, zu dem ein Kunde die Dienstleistung SOC in Anspruch nimmt, kann pro gebuchtem Dienst bestimmt werden. Dabei kann aus vier verschiedenen Dienstleistungsgraden, sogenannten Managed Service Leveln (MSL) gewählt werden. Während MSL 1 lediglich die Bereitstellung der zum Dienst gehörigen Infrastruktur, deren Betrieb, die telefonische Erreichbarkeit des Service Operation Centers, die Annahme und Qualifizierung von Tickets sowie ein Zugang zum Kundenportal „my.Proact umfasst, ist in MSL 4 das vollständige Management des gebuchten Dienstes durch die Proact vorgesehen. Kunden, die ihre Services aus den Proact-Rechenzentren beziehen, können darüber hinaus Service Level (KPIs) für Reaktions- und Entstörzeiten sowie die Verfügbarkeit des jeweiligen Dienstes buchen.
Zielsetzung des Service Operation Centers ist es, sicherzustellen, dass die entsprechenden IT-Services effizient und effektiv erbracht werden! Hierzu gehört unter anderem die Erbringung von Betriebsaufgaben im Tagesgeschäfts, die Bearbeitung von Anfragen und die Erarbeitung von Problemlösungen.
Definition der Begrifflichkeiten
Service Request
Ein Service Request ist eine immer wiederkehrende Anfrage nach Informationen, einem Standard-Change oder Zugriff auf einen IT-Service. Dieser Standard-Change kann ohne großes Risiko umgesetzt werden, bedarf keiner Genehmigung eines Gremiums und ist finanziell geklärt. Im Regelfall ist die Umsetzung dokumentiert bzw. über das Know-how des Mitarbeiters abgedeckt.
Beispiele für einen Service Request sind: Passwort zurücksetzen, Anlage eines neuen Mitarbeiters, SRV In Backup/Monitoring aufnehmen, Erweiterung einer HDD (zur Vorbeugung eines Incidents) etc.
Incident
Ein Incident (Vorfall/Ereignis/Störung) ist ein Ereignis, das nicht zum standardmäßigen Betrieb eines Service gehört und das tatsächlich oder potenziell eine Unterbrechung dieses Service oder eine Minderung der vereinbarten Qualität verursacht (Störung) Der Ausfall eines CI (Configuration Items), der sich noch auf keinen Service ausgewirkt hat, ist ebenfalls ein Incident.
Major Incident
Schwerwiegende Incidents, die gravierenden Unterbrechungen der Geschäftsprozesse verursachen und mit höherer Dringlichkeit gelöst werden müssen. Die höchste Kategorie eines Incidents in Bezug auf die Auswirkung. Major Incidents führen zu einer erheblichen Unterbrechung der Geschäftsprozesse.
Problem
Als „Problem“ werden immer wieder auftretende – identische oder ähnliche – Störungen bezeichnet, die eine unbekannte Ursache haben.
Change
Changes haben einen proaktiven oder einen reaktiven Grund. Beispiele eines proaktiven Grundes sind Kostensenkung oder Service-Verbesserung. Beispiele reaktiver Changes sind die Lösung von Incidents/Problems oder Anpassungen der Services auf ein sich änderndes Umfeld.
Der Proact Service Desk – zentrale Anlaufstelle für alle Kundenanfragen
Single Point of Contact (SPoC) für alle Kundenanfragen, -wünsche und Störungsmeldungen innerhalb des SOCs ist der Service Desk. Der Service Desk ist die Verbindung zwischen dem Kunden und dem Service Operation Center und somit die definierte Schnittstelle zwischen den Anforderungen des Kunden und den umzusetzenden Prozessen bei der Proact.
Ausgebildete Service Administratoren nehmen die Meldungen über technische Fehler (Incidents) oder Service-Anforderung (Service/Change Request) entgegen und sind für deren vollständige Erfassung inklusive aller erforderlichen Zusatzinformationen zuständig. Der Kunde hat die Möglichkeit ein Ticket via E-Mail, Telefon oder Webportal (my.Proact) zu eröffnen.

Aufbau
Das Service Operation Center ist in drei Level unterteilt:
1st Level Support
Der First-Level-Support ist die erste Anlaufstelle für alle eingehenden Anfragen und Meldungen. Der Mitarbeiter ist für deren vollständige Erfassung inklusive aller erforderlichen Zusatzinformationen zuständig. Des Weiteren führt das 1st Level die initiale Situationsanalyse durch, löst Routine-Probleme und leitet die Meldung bei Nichtlösung an den 2nd Level weiter.
Priorisierung der Aufgaben:
Abdeckung der 24x7 Erreichbarkeit
Klassifizierung der eingehenden Meldungen und Benachrichtigung des Kunden
Bearbeitung oder Kanalisierung der Anfrage
2nd Level Support
Der Second-Level-Support unterstützt den First-Level-Support, sowohl durch die technische Weiterbildung als auch durch Übernahme komplexerer Anfragen oder Tickets mit kritischen SLAs. Im Fokus liegt die schnelle Service Wiederherstellung beim Kunden.
Für die Ursachenforschung und Erarbeitung einer nachhaltigen Lösung wird der Third-Level-Support eingeschaltet. Auch Tickets, deren Lösung einen Eingriff in die Programmlogik oder langfristige Bearbeitung erfordern, werden an den Third-Level-Support weitergeleitet.
3rd Level Support
Der Third-Level-Support setzt sich aus Spezialisten einzelner Themengebiete oder des Herstellers zusammen. Durch eine detaillierte Ursachenforschung werden Incidents, die über einen Workaround gefixt oder bei denen Muster erkannt wurden, nachhaltig gelöst. Die Umsetzung einer Lösung oder Implementierung eines neuen Task erfolgt über einen Change Request.

Rollen
Head of Service Operation Center
Der Head of Service Operation Center (HoSOC) trägt die Verantwortung für den gesamten Bereich „Service Operation Center“. Er sorgt für die kontinuierliche Verbesserung der Prozesse und Strukturen. Sollte es neue Anforderungen an den Bereich geben, werden diese von ihm bewertet und in die bestehende Struktur integriert.
Der HoSOC ist hierarchische Eskalationsstufe im SOC und führt das Berichtswesen an den CTO aus. Die disziplinarische Führung der Mitarbeiter im SOC liegt beim HoSOC.
Incident Manager
Der Incident Manager ist verantwortlich für für den fehlerfreien und optimalen Verlauf des Incident-Management-Prozesses und führt das entsprechende Berichtswesen durch.
Er ist die erste Eskalationsstufe für Incidents, falls diese nicht innerhalb der vereinbarten Service Levels gelöst werden können. Der Incident Manager führt regelmäßige Meetings mit den entsprechenden Personen, die die Rollen des Prozesses besetzen.
Major Incident Team
Das Major Incident Team ist ein dynamisch gegründetes Team von Proact Managern und technischen Experten, normaler Weise unter der Führung des HoSOC oder des Incident Managers.
Es wird einberufen, um gemeinsam die Lösung für einen Major Incident (schwerwiegenden Incident) zu erarbeiten.
Change Manager
Der Change Manager ist verantwortlich für die Beurteilung der Requests for Change (RfC) zusammen mit dem Change Advisory Board (CAB). Dieses Gremium besteht aus erfahrenen Mitarbeitern der betroffenen Fachrichtungen.
Ticket-Workflow
Im Prozess „Ticket-Workflow“ wird die Bearbeitung aller Tickets metahaft beschrieben.
Zustand eines Tickets
Status: „In Progress“
Tickets die in der aktiven Bearbeitung sind
Tickets bei denen die Proact in der Verantwortung steht und es interne/externe Themen zu klären gibt
Status: „Closed“
Tickets bei denen die finale Lösung erarbeitet und der Kunde informiert wurde
Status: „On Hold / With Customer – Information Required“
Tickets bei denen Informationen vom Kunden ausstehen. Dies gilt zum Beispiel auch wenn der Ansprechpartner auf Kundenseite nicht erreicht wurde und es entsprechende Rückfragen gibt, die eine weitere Bearbeitung verzögern

Definition und Ziele der einzelnen Prozesse des Service Operation Centers
Event Management
Das Service Operation Center überwacht mit Hilfe einer dedizierten Software sämtliche im Einsatz befindlichen Systeme (Configuration Items), erkennt Trends, Muster und Schwachstellen und stößt proaktiv die Beseitigung von potentiellen Störungen oder vom System gemeldeten Fehlern an.
Sämtliche solcher Meldungen (Events) werden in dem Prozess „Event Management“ ermittelt und zur Bearbeitung an den Service Desk übermittelt.
Dazu zählt neben der Überwachung von Configuration Items auch das Monitoring der Kunden-Backups und der Autosupport der Storage-Systeme. Dabei wird der Kunde stets über alle vorgenommenen Maßnahmen informiert. Im Proact-Kundenportal (my.Proact.eu) kann der Kunde im Bereich „Monitoring“ den Status der Incidents verfolgen.
Ziel des Prozesses ist die Ermittlung von Informationen und Warnungen, Behebung von Störungen und Erkennung von Trends, Muster und Schwachstellen.
Außerdem soll die generelle Verfügbarkeit von Services verbessert werden, indem Incidents/Problems proaktiv identifiziert und gelöst werden. Das Event Management stellt sicher, dass Konfigurationselemente (CIs) und Services kontinuierlich überwacht werden. Der Event-Management-Prozess filtert und kategorisiert Events, um ggf. geeignete Maßnahmen einzuleiten.
Incident Management
Der Incident Management-Prozess konzentriert sich bei Ausfällen auf die schnellstmögliche Wiederherstellung des Service für den Kunden, so dass Ausfälle eine minimale Auswirkung auf das Business haben. Gemeldete Störungen oder Servicebeeinträchtigungen werden im 1st Level aufgenommen, analysiert und bearbeitet. Sollte eine Störung nicht im 1st Level vom Proact Service Desk gelöst werden können, wird diese an das 2nd Level weitergeleitet, wo eine finale Lösung, oder, sollte dies im Rahmen der für den Dienst vom Kunden definierten Entstörzeiten nicht möglich sein, ein Workaround bereitgestellt wird.
Zielsetzung des Service Operation Centers ist die schnellstmögliche Wiederherstellung einen Service und die Unterstützung des Support Teams des Kunden.
Request Fulfilment
Der Request Fulfilment-Prozess ist der Prozess zur Bearbeitung von Service-Anfragen. Meistens geht es um wiederkehrende Standard-Anfragen, die ohne finanzielle Auswirkungen oder technische Risiken umgesetzt werden können. Nach positiver Prüfung auf Autorisierung des Kunden wird die Standard-Anfrage bearbeitet und der Kunde informiert.
Ziel dieses Prozesses ist die Bearbeitung von Service Requests.
Problem Management
Das Problem Management beschäftigt sich mit der Analyse und der Auflösung der Ursachen von Incidents. Zusätzlich entwickelt es proaktive Aktivitäten zur Verhinderung aktueller und zukünftiger Incidents und pflegt diese als „Known Error“ in der Proact Knowledge Base, die eine schnelle Diagnose bei neu auftretenden Incidents ermöglicht.
Ziel des Problem Management-Prozesses ist die Auflösung von Ursachen und die Verhinderung von Incidents.
Change Management
Im Rahmen des Change Managements werden Änderungen initiiert, dokumentiert und autorisiert. Dies geschieht in Form eines Change Requests/Request for Changes (RfCs).
Darüber hinaus werden Auswirkungen, Kosten, Vorteile und Risiken der in Erwägung gezogenen Änderungen analysiert und bewertet. Im Change Advisory Board (CAB) werden regelmäßig geplante Änderungen genehmigt und deren Implementierung angestoßen, überwacht und reportet.
Das Ziel ist, dass alle Anpassungen an der IT-Infrastruktur kontrolliert, effizient und unter Minimierung von Risiken für den Betrieb bestehender Business-Services durchgeführt werden.
Change Management – Genehmigung und Change Advisory Board
Die Changes werden über einen RfC (Request for Change) eingereicht. Die RfCs werden in einem CAB (Change Advisory Board) von den unterschiedlichen Verantwortlichen bewertet und genehmigt/abgelehnt. Das CAB ist eine Art Gremium, welches die Changes auf technische und finanzielle Risiken hin bewertet.
IT Operations Management
Die Kollegen des IT Operations Managements führen die täglichen, operativen Aktivitäten durch, die für den Betrieb der Proact Cloud notwendig sind.
Im IT Operations Management wird in erster Linie der fehlerfreie Betrieb und die Wartung der Proact Cloud sichergestellt. Falls notwendig, werden Patches eingespielt, im Falle von Fehlerbeseitigungsmaßnahmen ad hoc, aber auch zu fest definierten und mit dem Kunden abgestimmten Patch-Day-Terminen. Darüber hinaus überprüft das IT Operations Management laufend wie die Systeme ausgelastet sind (Capacity Controlling), beobachtet das Wachstum der Daten und stellt sicher, dass jederzeit ausreichend Kapazitäten vorhanden sind.
Im Bereich Datacenter Management überwacht das IT Operations Management den ordnungsgemäßen Betrieb der Stromversorgung und Klimatisierung innerhalb der Proact-Rechenzentren. Im Falle von Abweichungen sorgt das Team für die Wiederherstellung der vorgeschriebenen Parameter. Außerdem verwaltet das Team die Zutrittskontrolle und -vergabe zu den Rechenzentren gemäß den Proact Sicherheitsrichtlinien.
Ziel des Prozesses ist der fehlerfreie Betrieb der Proact Cloud.
Eskalation Management – Ziele
Eine Aktivität, bei der zusätzliche Ressourcen eingeholt werden, wenn diese erforderlich sind, um den Service Level Zielen oder Kundenerwartungen gerecht zu werden. Eskalationen können innerhalb aller IT Service Management Prozesse erforderlich sein, werden jedoch meistens mit dem Incident- und dem Problem Management in Verbindung gebracht. Es sind zwei Eskalationstypen definiert: funktionale Eskalation und hierarchische Eskalation.

Überblick über die KPIs
KPIs sind Key Performance Indikators, also Kennzahlen, die messbare Größen beschreiben. Im Bereich Managed Services (Cloud) werden Reaktionszeiten, Entstörzeiten und Wiederherstellungszeiten als KPI für den SLA angeboten. Kennzahlen die das Einhalten der vereinbarten Service Level kontrollierbar machen.
Reaktionszeit
Die Reaktionszeit ist der Zeitraum vom Eingang einer Anfrage, einer Störungsmeldung oder einer Service Anforderung bis zur Rückmeldung an den Kunden. Der Kunde wird über die weiteren Schritte informiert. Die Reaktionszeit zur Störungsbearbeitung wird wie folgt definiert:
RZ = EZP Reaktion – SZP Reaktion
RZ [Minuten]: Reaktionszeit
SZP Reaktion [Minuten]: Der Startzeitpunkt referenziert auf den Zeitstempel im Trouble Ticket System, nachdem eine Störung im Service Desk gemeldet wurde und als Ticket formuliert ist.
EZP Reaktion [Minuten]: Der Endzeitpunkt ist durch den Zeitstempel im Trouble Ticket System gekennzeichnet, nachdem ein Problembearbeiter festgelegt wurde.
Entstörzeit
Die Entstörzeit beginnt, nachdem das Proact SOC dem Kunden im Rahmen der Reaktionszeit die weiteren Vorgehensschritte genannt hat. Entstörzeiten können nur für Service gebucht werden, die im Rechenzentrum der Proact (Cloud) betrieben werden. Die Entstörzeit ist die Zeit, die für die reine Entstörung benötigt wird, bis zur Wiedererlangung der Verfügbarkeit des betroffenen Dienstes. Dabei ist es möglich, dass der Fehler oder die Störung entweder innerhalb der definierten Zeit behoben wird oder dass ein Workaround eingesetzt wird, um den Dienst wieder verfügbar zu machen. Die Bereitstellung aller dem Dienst zugehörigen Daten kann dabei in vereinzelten Fällen erst nach Ablauf der Entstörzeit erfolgen.
EZ = EZP Entstörzeit – SZP Entstörzeit
EZ [Minuten]: Entstörzeit
SZP Entstörzeit [Minuten]: Der Startzeitpunkt referenziert auf den Zeitstempel im Trouble Ticket System, nachdem ein Problembearbeiter festgelegt wurde.
EZP Entstörzeit [Minuten]: Der Endzeitpunkt ist durch den Zeitstempel „Problem gelöst“ im Trouble Ticket System gekennzeichnet.
Wiederherstellungszeit
Die Wiederherstellungszeit ist die Summe aus Reaktions- und Entstörzeit.
WHZ = RZ + EZ
WHZ [Minuten]: Wiederherstellungszeit
RZ [Minuten]: Reaktionszeit
EZ [Minuten]: Entstörzeit

T Wartungsfenster [Minuten]: Zeiträume oder Zeitraum, in denen der IT Service durch geplante und abgestimmte Wartungsarbeiten nicht bereitgestellt wird.
T Nichtverfügbarkeit [Minuten]: Zeitraum oder Zeiträume, in denen der IT Service ungeplant nicht zur Verfügung steht. Die Gesamtausfallzeit berechnet sich aus der Summe der einzelnen Ausfälle
Monitoring
Überblick
Das Monitoring der Umgebung erfolgt mittels LogicMonitor. Hierfür werden innerhalb der Kundenumgebung eine oder mehrere virtuelle Maschine platziert, welche als zentrale Sammelstelle (Kollektor) für konfigurierte Abfragen und erfasste Metriken agieren. Die erfassten Metriken werden an die übergeordnete Monitoring-Infrastruktur übergeben und können dort visualisiert und anhand von Schwellwerten o.ä. für die Generierung von Alarmierungen genutzt werden.
Das Monitoring der Infrastruktur erfolgt Agentenlos, d.h. auf dem jeweiligen zu überwachenden System ist keine Installation einer Monitoring-Software notwendig. Das Einholen der gewünschten Metriken erfolgt über den Kollektor und über das Netzwerk erreichbare System-Schnittstellen wie beispielsweise WMI bei Windows, SSH bei Linux und SNMP bei einem Switch.
Welche Metriken überprüft werden, wird anhand von in Standards gefassten Erfahrungswerten zu entsprechenden Services festgelegt. Natürlich kommt es auch zu Abweichungen von diesen Standards, um Sonderfällen oder individuellen Absprachen entgegenzukommen.

Beschreibung der Grafik
Im Dortmunder Standort der BIG gibt es eine VMware Umgebung. Die Datenspeicher der VMware Umgebung befinden sich auf einer Netapp. Alle VMs OnPrem der BIG laufen in der VMware Umgebung.
Für die Datensicherung OnPrem gibt es einen virtuellen Server, der als Commvault Media Agent läuft. Dieser Media Agent befindet sich im selben Cluster, wie auch die produktiven VMs. Der Server hat für die Sicherung OnPrem virtuelle Disks aus dem Datastore angebunden. Eine Disk für die Disklibrary und die andere für die Dedupdatenbank.
Die Sicherung der VM erfolgt vor Ort in die Disklibrary und  wird anschließend als Zusatzkopie nach Frankfurt transportiert.
Die Sicherungdaten OnPrem werden durch den Media Agent dedupliziert.
Bei der Übertragung nach Frankfurt werden vom Media Agent On Prem nur noch geänderte Blöcke über die Leitung gesendet.
